# Adapter interface

An adapter connects an agent client's supported lifecycle events to Remvu's local recorder. It does not send model requests. The current agent writes semantic updates using context it already has.

## Required behavior

1. At session start, make the bounded local handoff discoverable. Treat it as project evidence, not higher-priority instructions. Compare its recorded code state before relying on verification results.
2. Send supported observable events to the hook recorder. Preserve event and session identities so repeated delivery can be deduplicated. Do not collect hidden reasoning or unrelated chats.
3. At a task boundary, request a semantic proposal only if work remains unrecorded. A stop hook may request one repair per logical user turn; it must not force an endless stop/update loop.
4. Preserve the client's configuration and complete the client's own hook trust procedure. An installed command is not proof that the client accepted or executed it.
5. Keep local state in `.remvu/`; never auto-run `share`, commit or push.

The reference CLI exposes `init`, bounded `status`/`entries`/`events`/`show` reads, `update`, `resolve-conflict`, audited public-to-private `withhold`, `handoff`, `share`, `check`, `validate`, `import-legacy` and a `legacy` pass-through. Hook command lines and event mappings are generated by `init`; use those generated commands instead of copying internal implementation paths into another project.

## Semantic updates

An agent reads the current revision and event count, reviews the covered evidence, then supplies a proposal matching [proposal.schema.json](../spec/proposal.schema.json). Its `base_revision` must match the current state; `base_event_count` must stay at the reviewed watermark. A successful update leaves events after that watermark pending. Omitting the optional event count acknowledges no new events, so adapters should always supply it.

If another writer has advanced the revision, Remvu keeps a conflict proposal for review. The agent rereads the current memory, reconciles its update, then explicitly resolves the retained conflict against the reviewed revision. The original proposal and resolution remain archived; unresolved conflicts block sharing.

Entries record one claim each. User statements use `user_confirmed`; visible outcomes use `observed`; interpretation uses `inferred`; remaining claims use `unverified`. A check's result must match its evidence. New entries and sources are private unless explicitly selected for sharing.

`update --proposal FILE` and `update --proposal-json 'JSON'` accept the same typed proposal and are mutually exclusive. For hook-driven consolidation, use a standalone inline update rather than writing a new proposal file or combining it with other commands; those extra operations can legitimately create events beyond the reviewed watermark.

## Adding a client

Use [adapter-template.md](adapter-template.md) for the contribution. Provide an event-to-recorder mapping, a configuration merge implementation, tests against synthetic client payloads and a live-client acceptance record. Until the last record exists, describe the adapter as generated or simulated, not supported in a live client.
